# Use Case 2 — Return to the Operating Room (RTOR) Clinical Abstraction

A **second, parallel use case** for the Foundry Fine-Tuning Accelerator. Where the
primary track ("Acme Health" member services) teaches the fine-tuning lifecycle on a
**customer-service** task, this track applies the *same* lifecycle to a **clinical
quality-abstraction** task: reading a patient timeline + operative notes and deciding
whether a surgery is an unplanned **Return to the Operating Room (RTOR)**.

It mirrors a real production pattern — batch-classifying surgical episodes over a
pandas DataFrame, emitting strict `{"is_return_to_or", "evidence"}` JSON with robust
parsing — and shows how fine-tuning + evaluation make that pattern cheaper, faster,
and more reliable than prompting a frontier model.

> ⚠️ **All data here is 100% synthetic and PHI-free.** The cases, timelines, and
> operative notes were authored for this demo. Nothing is derived from real patients.

## The task

Given, per surgical episode:

- a **patient timeline** (event log with day offsets),
- a **progress note**,
- the **index surgery** procedure description + operative note,
- the **current surgery** procedure description + operative note,

the model must output **only**:

```json
{ "is_return_to_or": true, "evidence": "…verbatim decisive sentence + which rule it triggers…" }
```

### Abstraction rules (the hard part)

Real abstraction is rule-governed and conflict-laden. The rules live in
[data/rtor_rules.md](../data/rtor_rules.md) and are embedded in the system prompt:

1. **Rule 1 — conflict-resolution priority** (first match wins): planned/staged → `false`
   even within 30 days; unplanned + related complication + within 30 days → `true`;
   unrelated anatomy/new diagnosis → `false`; outside 30 days → `false`.
2. **Rule 2 — operating-room requirement**: bedside / ICU / IR / endoscopy / clinic
   procedures do **not** count.
3. **Rule 3 — evidence requirement**: quote the single decisive sentence verbatim and
   name the rule it triggers.

Case `RTOR-0013` is deliberately tricky: a reoperation **within 30 days** that is
**planned/staged**, so the correct answer is `false` — it tests whether the model
honors the Rule 1 priority override instead of pattern-matching on "within 30 days".

## How it maps to the lab lifecycle

| Notebook | Lifecycle stage | What it does for RTOR |
|---|---|---|
| `00_synthetic_data_generation.ipynb` | Data | Loads the 16 labeled synthetic cases + rules KB, builds the system/user prompt + safe JSON parser, (optionally) augments via the base model, and emits `rtor_training.jsonl` / `rtor_validation.jsonl` / `rtor_eval.jsonl`. |
| `01_supervised_fine_tuning.ipynb` | Train | Shows the base model failing the tricky staged case, then submits an SFT job, deploys the fine-tuned model, and re-checks. **Submits a billable Azure job.** |
| `03_tool_calling_fine_tuning.ipynb` | Tools | Batch-classifies the cases over a pandas DataFrame (the production pattern), and emits tool-calling training data using `classify_return_to_or` + `flag_for_human_review`. |
| `07_evaluation.ipynb` | Prove | Scores precision / recall / F1 / accuracy vs. gold labels, plus an LLM-as-judge check on evidence groundedness, and prints a scoreboard. |

## Data files (in [`../data/`](../data))

- `rtor_rules.md` — the abstraction-rules knowledge base.
- `rtor_cases.jsonl` — 16 labeled synthetic cases (7 RTOR-true, 9 RTOR-false).
- `rtor_tools_schema.json` — function schemas for the tool-calling lab.
- `rtor_training.jsonl` / `rtor_validation.jsonl` / `rtor_eval.jsonl` — generated by Lab 00.

## Running

Same environment and prerequisites as the primary track (see
[`../README.md`](../README.md)): an active `az login`, the project `.venv`, and the
`AZURE_OPENAI_ENDPOINT` env var. Notebooks are path-agnostic — they work whether the
kernel starts in `fine-tuning/` or `fine-tuning/clinical-rtor/`.

**Preflight (get a green light first).** Either run the standalone check from a
terminal, or just run **Step 0** at the top of Lab 00 — both verify data files, SDKs,
your endpoint, `az login`, and a tiny call to the base model:

```powershell
python fine-tuning/clinical-rtor/preflight.py
```

It hard-fails only on missing local files; the Azure checks are advisory, so Lab 00's
offline data path still runs even before you have credentials. `GREEN` = ready for all
labs; `AMBER` = set `AZURE_OPENAI_ENDPOINT` and run `az login` before Labs 01/03/07.

- **Labs 00, 03, 07** run against base `gpt-4o-mini` in minutes and incur only
  inference cost.
- **Lab 01** submits a real SFT training job and deploys a model — expect training
  time and training/hosting charges. It is idempotent (re-running reuses the job via
  a marker file) and includes a cleanup step.
